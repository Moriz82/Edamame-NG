# Windows UAC and SYSTEM acceptance — 2026-09-25

Disposable Windows Server 2022 VM 1730 was cloned from stopped lab source guest on isolated Proxmox. It used isolated bridge `lab-net-08` with no uplink. UAC was enabled only in the clone. A temporary local Administrator account logged into console session 1. Its starting token had Medium Mandatory Level and `BUILTIN\Administrators` marked deny-only. The production VMs were not used for these tests.

| Check | Observed result |
| --- | --- |
| UAC Administrator route | Run `20260925T102953Z-LAB-WKS01-5364` started from the filtered console token with an empty offline tool directory. A visible UAC prompt was approved. `uac-admin` wrote a proof marker, returned 0, and opened an interactive high-integrity Administrator PowerShell. `whoami /groups` showed the Administrators SID enabled and High Mandatory Level. |
| UAC Resume | Resume asked for UAC consent again, returned 0, appended `resumed-proof`, and left the run count at one. A separate interactive Resume opened the elevated Administrator shell. |
| Consent refusal | Refusing UAC returned 1 and removed the stale proof marker. The tested fix recorded a retryable UAC failure instead of a false prerequisite failure; a later approved Resume returned 0. The consolidated `resume-elevation-not-completed` status was verified in the later hardening retest below. |
| Signed PsExec source | The [official PsTools ZIP](https://learn.microsoft.com/en-us/sysinternals/downloads/psexec) had SHA-256 `2b10b3d9dae0403b06d90b13bfb53e723a8b14a788f78cdfd43a445d8991415e`. Its `PsExec64.exe` v2.43 had SHA-256 `edfae1a69522f87b12c6dac3225d930e4848832e3c551ee1e7d31736bf4525ef`; Windows reported a valid Microsoft Corporation Authenticode signature. This binary was used as a verified offline fixture, not committed. |
| UAC to SYSTEM | Run `20260925T104717Z-LAB-WKS01-4120` began from the Medium token, used `-ApproveSystemService`, and required visible UAC consent. The `uac-admin-system` recipe returned 0 only after a child with SID `S-1-5-18` wrote the private marker. `success.json` saved the recipe ID and evidence only. |
| SYSTEM Resume and shell | No-shell Resume rechecked the signed saved PsExec binary and returned 0 without adding a run directory. Interactive Resume opened a session 1 PowerShell; `whoami` printed `nt authority\system`. [Console screenshot](uac-to-system-shell-2026-09-25.png). |
| Approval and tamper gates | A Resume with service approval declined returned 1 and recorded `resume-service-approval-declined` before UAC or service launch. Appending bytes to the saved PsExec binary made Resume return 1 with `resume-psexec-unavailable`; the original verified copy was restored before later tests. |
| Elevated Administrator to SYSTEM | The first direct attempt exposed a PowerShell 5.1 stderr handling bug: PsExec progress text was treated as terminating. After correction, run `20260925T105530Z-LAB-WKS01-5340` saved `admin-system` only after SID `S-1-5-18` proof. Resume rechecked the binary and returned 0 without enumeration. |
| PowerShell 5.1 tests | Parse/release/digest/cache, captured-process timeout, and private ACL/Resume tests passed in the clone. `tests/test_psexec.ps1` passed official ZIP extraction, signature and digest checks, cache fallback, and tampered-cache rejection using the downloaded ZIP as an offline fixture. |

The targeted UAC runs intentionally lacked WinPEAS, PrivescCheck, and SharpHound assets. Those rows stayed unavailable or unsupported; this test does not count them as completed enumeration. Earlier disposable Windows matrix runs cover those enumerators. The accepted SYSTEM routes require an administrator token or membership plus UAC consent. A standard-user to SYSTEM recipe, automatic credential validation, and broadly portable Windows CVE exploitation remain unsupported.

The temporary `PSEXESVC` service and the exploratory scheduled task were absent after testing. The successful SYSTEM run directory granted explicit full control only to the test account and SYSTEM. VM 1730, its ZFS disks and config, bridge `lab-net-08`, the temporary HTTP stage, and local staging files were removed. non-test guests remained running, source guests remained stopped, and `labpool` was healthy.

## Hardening retest on a fresh isolated clone

The reviewed route was retested on a new full clone of stopped source guest, again numbered 1730, on `lab-net-08` without an uplink. A disposable local Administrator logged into console session 1 with UAC enabled. The current code resolves and checks the signed System32 PowerShell binary before elevation, accepts only the reviewed PsExec64.exe v2.43 SHA-256 `edfae1a69522f87b12c6dac3225d930e4848832e3c551ee1e7d31736bf4525ef`, and creates a fresh proof filename per attempt. The interactive PowerShell process itself writes the SID marker before remaining open with `-NoExit`.

| Check | Observed result |
| --- | --- |
| First attempt | The first account setup and console-keyboard attempt left a UAC prompt pending. Its process was stopped; no `success.json` or proof marker was recorded. The exact reason for the pending prompt was not established. The disposable account was given a generated, unprinted password, and later UAC clicks used QMP input into the visible console. |
| UAC to SYSTEM | Run `20260925T112824Z-LAB-WKS01-3488` selected `uac-admin-system` from a filtered local Administrator token. After visible UAC consent, it recorded `proof-success` and a unique marker containing SID `S-1-5-18`. `success.json` contained host, recipe ID, and evidence label only. |
| Resume without enumeration | Two successful Resumes appended `resumed-proof` to the same run; no new run directory was created. Each produced a different `system-proof-<GUID>.txt` file. |
| Interactive SYSTEM shell | One Resume omitted `-NoShell`; the PowerShell process stayed open on the console and `whoami` returned `nt authority\system`. [Hardening retest screenshot](system-shell-after-hardening-2026-09-25.png). |
| Declined UAC | Clicking No on a later Resume appended `resume-elevation-not-completed`; it produced no new proof marker. This verifies the final renamed status. |
| Service approval and tamper gates | Declining the service prompt appended `resume-service-approval-declined` before UAC. Appending data to the saved PsExec made Resume append `resume-psexec-unavailable` without UAC. The verified binary was restored and its reviewed digest rechecked. |
| Elevated Administrator route | Run `20260925T114431Z-LAB-WKS01-4256` selected `admin-system` and recorded SID proof. Its Resume appended `resumed-proof`, skipped enumeration, and wrote a second unique marker. |
| Native tests | Windows PowerShell 5.1 parse/release/cache, capture/timeout, ACL/Resume selection, offline CVE catalog, and pinned PsExec asset/sidecar/marker tests all passed. Linux syntax, ShellCheck, Linux behavior, and catalog tests passed on the Mac. |
| Side effects and access | After the no-shell and interactive runs, `PSEXESVC` service query returned 1060; `C:\Windows\PSEXESVC.exe` and the service registry key were absent. The disposable user's `HKU\...\Software\Sysinternals\PsExec` key retained `EulaAccepted=1`. The successful run directory ACL granted full control only to that user and SYSTEM. |

This acceptance is specific to the Windows Server 2022 console guest. Client Windows, RDP and multiple sessions, interrupted service cleanup, and standard-user-to-SYSTEM behavior still need independent proof. Other checklist areas and credential validation remain explicitly unsupported where no reviewed recipe exists.

After the retest, VM 1730 was stopped, destroyed, and purged. Readback found no VM 1730 configuration or ZFS volume, `lab-net-08` was absent, the bridge-local HTTP service was inactive, and its staging directory was removed. non-test guests were still running, source guests were still stopped, and `zpool status -x` reported all pools healthy.
