# Windows weak-service fixture acceptance — 2026-09-25

## Scope and guest

This record covers the fixed `EdamameWeakSvc` disposable fixture, not arbitrary Windows services. Disposable Proxmox VM 1731 was a full clone of stopped source guest on an isolated `lab-net-09` bridge with no physical uplink. The guest reported Microsoft Windows Server 2022 Datacenter build 20348. Local user `edamame_lab` had SID ending `-1004`, was absent from local Administrators, and owned active console session 1. The account and VM were created solely for this test. QEMU Guest Agent was used to set up and inspect the fixture; escalation proof was launched from that standard-user console.

The exact service fixture was stopped, manual-start, configured as LocalSystem, and had a protected HKLM marker. The first fixture ID was `14493881bbf34ac6a4361c528eb25096`; after review fixes, it was recreated as `93bfe7aaa6db442991139944cf646d72` with the test user's SID bound into the marker. Its DACL granted that SID service query, change-config, query-status, and start rights (mask `0x17`). The runner checked effective rights through `OpenServiceW(0x17)`, plus the account, state, start type, marker, user SID, and original binary path before selection and again before mutation. For this route test, scans used an empty `-ToolDir`; external enumerators were explicitly unavailable in `coverage.tsv`. Earlier matrix records cover WinPEAS, PrivescCheck, and SharpHound operation.

The success file contains only host, `weak-service-lab`, service name, fixture ID, SYSTEM proof SID, and a restoration flag. It contains no payload command, nonce, pipe name, or credential. After the final no-shell proof and Resume, no encoded weak-service payload process remained. The service path was byte-identical to the marker's original path at every normal completion and while the interactive shell was open. A service start may still log SCM timeout 1053 because the temporary command is not a Windows service implementation; the proof depends on the independently verified SYSTEM client token and restored configuration, not `sc.exe` exit code.

## Limits and cleanup

Only Windows Server 2022 console session 1 and the exact fixture were accepted here. Client Windows, RDP or multiple sessions, arbitrary discovered services, and real-world service repair remain untested. A malicious user who already has change/start rights to a LocalSystem service can independently misuse that service; the fixture deliberately creates those rights for the test. The runner refuses service-path or account drift and does not assume that a WinPEAS or PrivescCheck string alone proves exploitability.

Cleanup completed: the guest reported no fixture marker and `sc query EdamameWeakSvc` returned 1060 before shutdown. Disposable VM 1731 and its ZFS volume, isolated `lab-net-09`, transient transfer server, and staging directory were destroyed. Readback found no VM configuration, volume, bridge, active transfer unit, or staging directory. The production non-test VMs and other test guests were still running, source guests were still stopped, and `zpool status -x` reported all pools healthy. The guest test account and raw run outputs were removed with the disposable VM.
